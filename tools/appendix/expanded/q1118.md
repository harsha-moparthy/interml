**An agent should stop because a verified success condition or a defined limit was reached.** “The model says done” is not sufficient evidence that an external action succeeded. Keep termination criteria in the application state so they can be checked consistently. [1]

For a code-fixing task, completion might require a specific test to pass and a patch to exist. For a retrieval task, it might require an answer supported by accessible sources. The criterion should describe observable results, rather than a vague instruction to keep trying until satisfied.

Use several budgets: maximum tool calls, generated tokens, elapsed time, monetary cost, and repeated failures. A limit on loop iterations alone misses a single tool call that hangs indefinitely. Tool timeouts and cancellation must therefore work independently of the model's next decision.

Consider a search loop that repeatedly reformulates the same query. Record normalized actions and whether they produced new useful evidence. If the last several attempts add nothing, the controller can change strategy, request missing information, or return a clearly incomplete result. A novelty heuristic is helpful, but it must not replace task-specific success checks.

**Retries need semantic care.** A timed-out payment or write may already have succeeded. Repeating it can create duplicate effects. Use idempotency keys or inspect the external state before retrying; exponential backoff alone does not solve duplicate execution. [2]

Finally, separate terminal states such as `completed`, `budget_exhausted`, `needs_input`, and `failed`. Preserve the evidence and partial work in each state, and report what remains unverified. Evaluate not only how often the agent eventually succeeds, but how often it falsely claims success, wastes actions, or leaves effects after cancellation. A reliable stopping rule is part of the task implementation, not a cosmetic sentence appended to the prompt. [3][4]
