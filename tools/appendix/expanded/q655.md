**Separate answering users from learning from them.** The serving system must respond predictably now. The training system can inspect feedback, prepare datasets, and evaluate future versions later. Updating model weights directly from each live thumbs-up/down would mix noisy feedback, deployment risk, and latency concerns into one uncontrolled loop.

**Follow one request.** Authenticate and validate it, estimate prompt/output work, admit it to a bounded queue, process the prompt, then stream generated tokens. A scheduler combines compatible requests to use the GPU efficiently. Requests with long histories need more KV-cache capacity than short requests, so a simple count of concurrent users is an incomplete capacity measure. [3]

**Follow one feedback event separately.** Record the prompt/context version, model version, answer, user signal, and any relevant consent/retention metadata. Later, deduplicate and review examples, form a training/evaluation split, train a candidate, and compare it against the current model. Only a validated candidate enters a canary rollout.

**Measure the user's experience in parts.** Time to first token determines how long the user waits before seeing anything. Inter-token latency determines whether streaming feels smooth. Total completion time depends on answer length. A system can improve throughput while making one of these worse, so report them separately under realistic load.

A fallback model, admission limits, cancellation, and rollback make failures manageable. Preference optimization changes behavior, but feedback is selective: users who vote are not necessarily representative, and a popular answer is not necessarily a correct one.

**Technical details and references.**

Separate the online serving path from the feedback/training path. Serve a versioned model behind admission control, bounded queues, streaming responses, and a scheduler that accounts for prompt and generated lengths. Continuous batching and paged KV storage improve utilization; prefix-cache reuse must include model revision, tokenization, and access scope in its identity. Track time to first token and inter-token latency separately from end-to-end time.

Log consented request/model versions and explicit ratings, edits, abandonment, and follow-up behavior. These signals are noisy: a user leaving may mean satisfaction or failure. Create preference pairs only when candidates share the same prompt and the preference is defensible; deduplicate, remove sensitive data, and separate users/time periods across splits. Human review can calibrate automated labels.

Train candidate SFT/DPO checkpoints offline, compare quality, safety, and latency on frozen and fresh evaluation sets, then shadow/canary with rollback. Never mutate production weights after each click. Continued training trades adaptation speed against label quality, reproducibility, and regression risk. Monitor feedback selection bias and model changes that improve ratings while degrading factual correctness.

**Mathematical and practical explanation.** Required KV bytes scale as $2LBSH_{kv}d_hb$ before allocator overhead. Admission control should therefore consider active token lengths, not only concurrent request count. Keep feedback datasets versioned and evaluate candidate preference-tuned models offline before a canary; live user feedback is selective evidence rather than a clean unbiased reward stream.
