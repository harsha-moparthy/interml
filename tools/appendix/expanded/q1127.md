**An artifact store holds files; a model registry organizes identifiable model versions and their lifecycle metadata.** A file named `best_model.bin` does not tell you which dataset produced it, what evaluation it passed, or whether it is compatible with the current inference code. [1]

A useful registered version points to the model artifact, training run, dataset snapshot, code revision, parameters, evaluation results, and input/output signature. The actual files may still live in an object store. The registry supplies relationships and version identity rather than replacing all storage.

For deployment, define a release bundle that includes preprocessing, tokenizer or feature definitions, model weights, inference code, dependency environment, and relevant configuration. Otherwise rolling back only the weights can leave a new tokenizer or scaler paired with an old model, producing incorrect predictions despite a successful file download.

Aliases such as `candidate` or `champion` can make selection convenient, but aliases are mutable. Record the resolved immutable version when a release starts. Two requests using an alias at different times may otherwise refer to different artifacts, making an incident difficult to reproduce.

**Promotion is an application policy.** A registry does not automatically prove that a model is fit for production. Define required validation, compatibility checks, owner decisions, and rollback criteria. Test loading the complete bundle in a clean environment and run a small set of representative predictions before shifting traffic. [2][3]

An illustrative failure is an apparently improved model whose feature order changed from `[age, income]` to `[income, age]`. Both columns are numeric, so the service may run without an exception while predictions become wrong. Versioned schemas and parity tests catch this better than a filename convention. The registry's value is traceable, reproducible selection; runtime monitoring is still needed after release. [4][5]
