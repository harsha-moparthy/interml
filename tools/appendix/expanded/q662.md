**Text-to-SQL has two problems: finding the right meaning and producing a safe query.** A syntactically valid SQL statement may answer the wrong business question, while a semantically correct query can be too expensive or use unauthorized data. Treat these as separate checks.

**Consider “What was revenue last quarter?”** The system must determine the fiscal/calendar period, currency, gross/net definition, refunds, and aggregation grain. Choosing a column named `revenue` from the first matching table is not enough. A semantic catalog containing approved metric definitions and join paths helps resolve these choices before generating SQL.

**Why schema retrieval is necessary.** With 10,000 tables, passing the entire catalog to a model is expensive and confusing. Route to the likely business domain, retrieve relevant tables and relationships, then generate within that narrowed context. Examples should be non-sensitive and representative, not a reason to expose arbitrary production rows. [3]

**Check the query before execution.** Enforce read-only access, allowed tables/columns, resource limits, and timeouts. Inspect joins that can multiply rows: joining orders to several line items and then summing an order total can double-count revenue while producing perfectly valid SQL.

Compare important questions against trusted queries and result checks. Keep clarification available when a business definition is ambiguous. Return the interpretation and relevant filters with the result so the user can see what was calculated. A fluent natural-language explanation cannot compensate for the wrong aggregation grain or a hidden permission violation.

**Technical details and references.**

Index schema names, descriptions, approved join paths, metric definitions, and representative non-sensitive value dictionaries. A domain router narrows the 10,000-table catalog; retrieve only relevant schema fragments and semantic definitions. Resolve ambiguous business concepts such as gross versus net revenue with clarification rather than inventing a metric.

Generate SQL in a typed intermediate structure or parse the output into an AST. Enforce one approved read query, allowed functions/tables, row/column permissions, row limits, and execution budgets. A read-only account is necessary but not sufficient: expensive joins and dangerous user-defined functions still need controls. Validate dialect syntax and use EXPLAIN/cost estimation before execution.

Allow a bounded repair loop using sanitized compiler/runtime errors. Log query text, schema/model versions, and lineage; redact sensitive result rows. Check aggregation grain, join multiplicity, and time filters with deterministic assertions or test queries. Evaluate execution accuracy against expected result sets, not just syntactic validity. Cache results only with tenant, permission, parameter, and data-freshness scope; return an explicit uncertainty when schema evidence is insufficient.

**Mathematical and practical explanation.** Separate semantic correctness from SQL validity. A query can parse and execute while joining at the wrong grain or using the wrong definition of revenue. Validate allowed tables/operations, query cost, join cardinality, and result plausibility; execute with read-only permissions and timeouts. Maintain golden question–query–result tests for important business metrics. [3](https://arxiv.org/abs/2005.11401)
