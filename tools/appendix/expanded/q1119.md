**Pass@k measures whether at least one of k generated candidates passes a correctness test.** It is useful for code generation when unit tests provide a functional check. It does not measure the probability that a deployed system can identify and return that correct candidate without a verifier. [1]

If a problem has $n$ sampled candidates and $c$ pass, the usual estimator for $k\le n$ is

$$\widehat{pass@k}=1-\frac{{n-c\choose k}}{{n\choose k}}.$$

The fraction is the probability that a uniformly selected subset of $k$ candidates contains only failures. Subtract it from one to obtain the chance of at least one success. If fewer than $k$ failures exist, the numerator is zero.

For $n=10$, $c=2$, and $k=3$, the estimate is $1-\binom83/\binom{10}3=1-56/120\approx0.533$. Pass@1 is $c/n=0.2$. The improvement reflects more attempts, not an improvement in the underlying model's single-attempt behavior.

Under independent sampling from the same generation distribution, the estimator is unbiased for the corresponding success-within-k quantity. Report the sampling policy, temperature, sample count, tests, and any filtering. Changing these changes the experiment. For many problems, estimate per problem and average; pooling all candidates first can incorrectly weight problems or obscure differences in difficulty.

**Limitations:** incomplete tests can accept incorrect programs, and repeated near-identical samples reduce practical diversity. Further, comparing model A at pass@100 with model B at pass@1 ignores a large inference-budget difference. Include a matched-budget comparison and, where relevant, the accuracy of the selection mechanism. Majority voting, best-of-k with an imperfect judge, and pass@k with an oracle test are distinct metrics and should not be reported interchangeably. [2][3]
